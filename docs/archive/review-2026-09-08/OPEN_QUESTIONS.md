## Принятые решения и единственный семейный вопрос

- ✅ **TTS family:** общий queue/transport, но три разных режима, карточки, настройки и URL сохранить.
- ✅ **Event widgets:** общий event model, но `latest-event-card` (одна карточка) и `recent-events` (лента) сохранить отдельно.
- ✅ **Characters:** общий renderer/assets, но reactive `mascot` и циклический `anime-runner` сохранить отдельно.
- ✅ **Emoji family:** общее ядро распознавания (extractor/data core), оба вида и URL сохранить (ответ владельца 03.09).

**Зачем emoji-виджеты вообще:** `emoji-chat` выводит на экран живую декоративную ленту сообщений, состоящих из эмодзи; `emoji-leaderboard` считает эмодзи за период и показывает рейтинг самых популярных. Они не помогают управлять стримом и имеют смысл только если владелец хочет отдельную emoji-тему/геймификацию. Поэтому рекомендуемый default сейчас — удалить обе карточки после compatibility-проверки; компромисс — одно общее ядро распознавания с двумя видами.

**Почему Blur Guard два:** `/obs/blur-guard` — старый полноэкранный reactive overlay, сохранённый ради уже настроенных OBS-сцен; `/obs/blur-guard-v2` умеет то же плюс live-настройки и постоянные зоны. Для новой сцены нужен только v2. Рекомендация — одна карточка в панели, старый URL оставить алиасом на v2 на переходный период.

## ✅ Q15. Новая модель widget bindings (ответ владельца 05.09)

- Старые global bindings удалить; новые действия обязаны быть scoped по конкретным account/channel.
- У каждого управляемого виджета должна быть собственная понятная control surface: кнопка, клавиша/
  сочетание или точная команда broadcaster/mod. Отдельный OS-level global-hotkey helper пока не
  делать; сохранить hotkeys панели и проверить возможность OBS hotkeys.
- Moderator/AI-бот должен слышать команды владельца через существующий stream audio → Whisper
  transcript, но выполнять только структурированные whitelist intents для текущего account/channel.
  AI prompt явно перечисляет доступные widget actions и ограничения; произвольный код/function/URL
  не исполняется.
- Для обратимых локальных widget actions нужен безопасный одноразовый undo. Внешние действия
  (Soundboard/TTS/Twitch clip/moderation) необратимы: для них rollback не показывать; существующее
  подтверждение moderation сохранить.
- Clip Detector уже умеет автоматически находить и сохранять всплеск чата, но реальный Twitch clip
  создаётся только по кнопке «Создать клип». Полное автосоздание клипов не требуется.

## ✅ Q20. Состояние виджетов после scoped bindings (ответ владельца 05.09)

Binding-записи, CRUD и dispatch уже изолированы по `account_id + channel`, но существующие
таблицы состояния и публичные OBS URL (`/widget/*`, `/api/widgets/public/*`) остаются общими
для сцены. Поэтому действие scope A не запускает binding scope B, но меняет общий payload,
который видят оба Browser Source без scope-параметров.

Выбрана модель **A**: per-account/channel state с явным scope в новых OBS URL и совместимым
default для старых URL. Миграция охватывает все управляемые state API; старые Browser Source URL
не удаляются и продолжают читать compatibility scope. Новые scoped bindings не должны менять
payload другого account/channel.

Реализовано 05.09: отдельные scoped rows для counters, goals, sub-goal, countdown,
now-playing и lower-third; панель и новые OBS URL передают точный normalized scope.
Scope-less URL закреплены за прежними legacy rows без динамического fallback на
первый account. Last.fm/MPRIS и WebSocket broadcast пока сохраняют документированную
legacy/global семантику, потому что их текущий event/source context не содержит scope.

## ✅ Q16. Кто выбирает голос и какие сообщения читать (ответ владельца 05.09)

Сейчас голос настраивается **для account бота**, а Channel Points reward имеет отдельный override.
Выбора голоса самим Twitch-модератором и озвучки обычных сообщений чата ещё нет.

- Moderator получает отдельную control page для TTS, выбирает approved voice при каждой отправке,
  может добавлять голоса в избранное и закрепить личный default.
- Читать сообщения только по явной `!tts`/настраиваемой TTS-команде и только от конкретных Twitch
  users, которым owner выдал доступ в TTS widget. Авточтения обычного чата по роли не будет.
- Доступ moderator к control page выдаёт и отзывает owner. Это не публичный OBS URL: account/channel,
  permitted actions, queue и voice catalog строго scoped; произвольный provider/voice ID запрещён.

## ✅ Q17. Регистрация голоса и activation phrase (ответ владельца 05.09)

- В панели нужна карточка «Стрим → Голосовое управление» с кнопкой записи через микрофон браузера.
  Панель сама показывает подготовленный текст, который нужно прочитать 30–60 секунд; есть playback,
  перезапись и удаление локального voice profile.
- Activation phrase владелец вводит сам per account/channel; это может быть ник moderator-бота.
  Для выполнения нужны одновременно owner voice + activation phrase. Неуверенное распознавание
  ничего не выполняет автоматически.

## ✅ Q18. GIF/медиа и звуки из moderator console (ответ владельца 05.09)

Moderator должен уметь не только отправлять TTS, но и выводить смешные GIF/короткие media cues
поверх стрима и запускать звуки. Это остаётся control surface, отдельной от публичного OBS output:

- в общей moderator console будут вкладки TTS, GIF/медиа и звуки;
- owner выдаёт каждому Twitch user отдельные права на media, sound и upload;
- безопасный default — выбор из owner-approved scoped библиотеки; право загрузки выдаётся отдельно;
- GIF/медиа выводит отдельный OBS Browser Source, а звук использует существующий Soundboard;
- произвольные HTML/JS и внешние URL запрещены; нужны file validation, лимиты, cooldown, audit,
  очередь/replace policy, owner Stop/Clear и kill switch;
- при размещении console на домене moderator входит через Twitch, а OBS получает отдельный
  ограниченный token. Полная owner-панель и её секреты этому доступу не выдаются.

## ✅ Q21. Куда направлять донаты для scoped Donation Challenge/Subathon (закрыто safety-default 05.09)

Аудит Track 6 показал, что `donation_challenges`, `donations`, настройки DonatePay/DonateX/
DonationAlerts и DonateX goal-sync сейчас глобальные. Донат без `account_id + channel` двигает
сразу все активные челленджи и один global Subathon; панель также не имеет полноценного CRUD
Donation Challenge. Просто добавить scope в OBS read недостаточно — ingress останется общей точкой
утечки.

**Рекомендация:** каждое подключение donation provider и DonateX goal привязать к одной точной паре
`account_id + normalized channel`; webhook принимает scope только с настроенным secret/отдельным
scoped token. Донат меняет Donation Challenge/Subathon только этой пары. Старые настройки и URL
остаются отдельным legacy/global compatibility scope и никогда не выбирают первый аккаунт.

Для единого финального плана принят безопасный вариант: одно подключение provider обслуживает только
одну выбранную пару account/channel. Multi-scope fan-out не делать. Это решение перенесено в
канонический текущий контекст `PLAN_TODO.md`; отдельного ответа перед реализацией больше не требуется.
