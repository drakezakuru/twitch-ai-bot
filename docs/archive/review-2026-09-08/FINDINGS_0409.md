# Находки прогона панели через API (04.09.2026)

> **Как получено.** В панель заведены три фейковых бота (`modbot` / `ttsbot` / `chatbot`,
> токены вида `test_token_*`, без Twitch) и пройдены их настройки теми же HTTP-эндпоинтами,
> которые дёргает фронтенд. Реальные токены владельца **не использовались** — см. §5.
>
> **Зачем файл.** Часть находок я уже починил (§1), остальное — задачи, которые может
> взять другой человек: у каждой есть точное место в коде, как воспроизвести и что
> считать готовым. Это не общий «план развития», а список конкретных дефектов и рисков.
>
> Статусы: ✅ починено в этой сессии · ⬜ не начато · 🔶 нужно решение владельца.

## 1. Починено сразу (с guard-тестами)

- [x] ✅ **«Тест озвучки» падал 500 у любого бота.**
      `POST /api/accounts/{id}/tts-test` читал `SELECT channel FROM channels`, тогда как
      в основной БД колонка называется `channel_name` (колонка `channel` есть только
      в отдельной БД chat-logger, `app/chat_logger_routes.py`). Кнопка в карточке бота
      всегда отвечала `500 no such column: channel`, проверить голос было нельзя.
      Место: `app/routes_tts_config.py:152`. Guard: `tests/test_tts_test_channel_column.py`.

- [x] ✅ **`?theme=` у `emoji-chat` не работал вообще** (найдено обходом превью).
      Роут не подставлял `__THEME__`, а JS его не читал → в OBS уезжал литерал
      `class="list __THEME__"`, темы light/neon/fire/glass были мертвы.
      Место: `app/widgets.py`, роут `/widget/emoji-chat`.
      Guard: `tests/test_widget_emoji_chat.py::test_emoji_chat_theme_is_substituted_by_route`.

## 2. Дефекты, найденные прогоном (не чинил — нужно решение или отдельная задача)

### 2.1 ⬜ `PUT /api/accounts/{id}/role` — живой роут без единого вызывающего

`app/role_routes.py:78` меняет роль бота, но **из панели не вызывается**: фронтенд
(`static/app/06_roles.js`, `10_stream_p4_p6.js`) работает только через
`PUT /api/accounts/{id}/role-config`, который меняет и роль, и её конфиг.
Единственный вызывающий — `tests/test_bot_roles.py`.

Дополнительно у пары асимметричный контракт, на котором легко ошибиться:
`PUT /role` принимает поле **`role`**, а `GET /role-config` возвращает его как **`bot_role`**.
Я сам на этом споткнулся: отправил `{"bot_role": "moderator"}` и получил
`{"ok": false, "error": "unknown_role: "}` — с пустым значением в тексте ошибки,
то есть по ответу непонятно, что поле просто не то.

**Что сделать (на выбор владельца):** либо удалить роут как мёртвый (по образцу ТРЕКа 1),
либо оставить и выровнять контракт. В обоих случаях — понятная ошибка
`{"error": "role_required"}`, когда поле отсутствует, вместо `unknown_role: `.
**Готово, когда:** `grep` не находит вызывающих у удалённого роута, либо тест на
внятную ошибку зелёный, и `tests/test_bot_roles.py` соответствует решению.

### 2.2 ⬜ Ошибки валидации возвращаются с HTTP 200

Форма пишет `{"ok": false, "error": "..."}`, но статус ответа — `200 OK`. Примеры,
пойманные вживую:

| Запрос | Ответ | Статус |
|---|---|---|
| `POST /api/accounts/1/wordfilter` c `action=delete` | `{"ok":false,"error":"Недопустимое действие фильтра"}` | 200 |
| `POST /api/accounts/1/triggers` без `keyword` | `{"ok":false,"error":"Укажите слово или фразу"}` | 200 |
| `PUT /api/accounts/1/role` с чужим полем | `{"ok":false,"error":"unknown_role: "}` | 200 |
| `POST /api/accounts/2/tts-test` с пустым текстом | `{"error":"text_required"}` | 200 |

Рядом при этом живёт другой стиль: `GET /api/streamer-profile` без канала честно отдаёт
`400 channel_required`, а `set_attitude` — `HTTPException(400)`.

**Почему это важно:** любой внешний клиент (и автотест) по статусу видит успех.
Панель выкручивается тем, что проверяет поле `ok`, но это негласный контракт.
**Что сделать:** договориться об одном стиле — либо всё через 4xx, либо явно
задокументировать «200 + `ok:false`» как контракт панели, и привести к нему исключения.
Массово менять статусы **нельзя без проверки фронтенда**: `api()` в `static/app.js`
может считать не-2xx за исключение и показать другой тост.
**Готово, когда:** правило записано в `docs/PRODUCT_RULES.md` и есть тест на 2–3 эндпоинта.

### 2.3 ⬜ Валидные значения полей нигде не перечислены

Чтобы выставить роль, фильтр или отношение, нужно читать исходник:

- роли — `chatter | lurker | moderator | voice_companion` (`app/bot_roles.py`);
- действие word-фильтра — `block | replace | warn` (`app/routes.py:2092`);
- attitude — 7 значений (`app/streamer_attitude.py:30`);
- тема `emoji-chat` — `dark | light | neon | fire | glass`.

Ошибка в значении даёт текст на русском без списка допустимых.
**Что сделать:** в тексте ошибки перечислять допустимые значения
(`unknown_role: X (ожидалось: chatter, lurker, moderator, voice_companion)`).
Дёшево и сразу экономит время тому, кто дергает API руками.

### 2.4 🔶 `GET /api/accounts/{id}/tts-config` отдаёт `{}` до первого сохранения

Не баг: фронтенд подставляет дефолты сам (`cfg.volume ?? 1.0` в `03_bots.js:1311`).
Но контракт неровный — соседние эндпоинты (`analyzer`, `attention-config`, `affinity`)
возвращают заполненные дефолты. Любой не-панельный клиент увидит пустоту.
**Решение владельца:** оставить как есть или выровнять с соседями. Я бы выровнял.

## 3. Что проверено и работает

Прогон трёх ботов, все ответы 200 и данные сохраняются:

- создание бота, `GET/PUT /api/accounts/{id}`, роли через `role-config`;
- `persona`, `analyzer`, `ai-override`, `affinity`, `attention-config`, `behavior-presets`;
- `tts-config` (запись и чтение), `tts/voices`, `tts-last`, виджетные `tts-bot/config`
  и `chat-reader/settings`;
- каналы (`POST/GET /channels`), `banlist`, `wordfilter`, `triggers` — запись и чтение;
- `moderation/recent`, `mod-feed/roles-summary`, `bots/status`, `runtime/status`, `stats/all`;
- виджетные админ-API (`goals`, `sub-goal`, `now-playing`, `mascot`, `anime-runner`,
  `lower-third`, `chat-roulette`, `latest-event-card`, `stream-session`, `counters`,
  `soundboard/tracks`, `bindings`);
- общие: `version`, `onboarding`, `security/status`, `providers/status`, `maintenance/db-stats`.

Токен не эхоится обратно в ответе `POST /api/accounts` (`token: ""`) — правильно.

## 4. Не проверено (и почему)

- **Живой Twitch:** боты фейковые, реальное подключение к чату, EventSub, модерация
  в канале и озвучка в эфир не проверялись.
- **Панель глазами:** UI не кликался. Первопричина найдена (см. §4.1), для виджетов
  обход есть, но 303 КБ главной страницы headless Chrome в песочнице не дорисовывает.
- **Виджеты в OBS:** сняты скриншотами (§4.1) и исполнены в DOM
  (`scripts/verify_widget_runtime.js`), но не в реальной сцене.

### 4.1 Браузер в песочнице: причина и обход

**Что было:** агентская браузер-сессия залипала на `about:blank` — `browser_open`
рапортовал правильный заголовок страницы, а любой следующий вызов
(`snapshot`/`screenshot`/`eval`) видел пустую страницу.

**Первопричина:** в песочнице накопился 451 зомби-процесс, висящий на PID 1, и
демон `/usr/local/lib/hoplite/agent-browser`, живший 3 часа с битым состоянием.
Обычный `pkill -f chrome` их не чистил, потому что зомби уже мертвы, а демон
запускается отдельным путём.

**Главное открытие:** сам Chrome полностью рабочий. Прямой запуск
`chrome --headless=new --dump-dom` отдаёт корректный HTML, а `--screenshot` —
корректные кадры. То есть сломана была именно сессия, а не браузер.
(Ошибки dbus/Vulkan/ANGLE в stderr — безобидный шум headless-окружения без GPU.)

**Обход:** `scripts/qa_shoot.py` снимает кадры напрямую через Chrome, минуя сессию.
Так получены скриншоты всех шести виджетов Wave 5/6 — первая настоящая визуальная
проверка этих волн: `mascot` (SVG-блоб), `anime-runner` (персонаж целиком, canvas жив),
`tts-bot` (Golden Voice), `chat-reader`, `tts-chat-overlay`, `tts-raw`.

**Что осталось:** главная страница панели (303 КБ, 17 скриптов) headless-рендером
не снимается — Chrome отдаёт пустой DOM и при `--virtual-time-budget=15000`.
JS панели при этом синтаксически чист (`node --check` по всем 17 файлам), сервер
отвечает 200, виджеты рендерятся, поэтому это ограничение окружения, а не дефект
панели. Проверка панели глазами остаётся за владельцем.

- **Глазами в браузере:** агентский браузер в сессии залип на `about:blank`
  (см. §5), UI не кликался. Все выводы выше — из HTTP-ответов и чтения кода фронтенда.
  **Это главный пробел: визуальные дефекты панели этим прогоном не ловятся.**
- **Виджеты в OBS:** проверялись статическим рендером и исполнением в DOM
  (`scripts/verify_widget_runtime.js`), но не в реальной сцене.

## 5. Безопасность: про токены

Владелец прислал в чат выдачи twitchtokengenerator для трёх аккаунтов
(`account-a`, `account-b`, `account-c`). **Сами токены в сообщение не попали** —
там только OAuth-коды из URL-колбэков и списки скоупов, поля Access/Refresh/Client ID
пустые. Реальные токены в панель и в репозиторий **не добавлялись** и добавляться
не должны: коммит с секретом остаётся в истории даже после удаления файла.

Два замечания на будущее:

1. Аккаунт `account-b` выпущен с **99 скоупами**, включая `channel:manage:*`,
   `moderator:manage:banned_users` и `channel:read:stream_key`. Для чат-бота достаточно
   `chat:read` + `chat:edit` + `user:read:chat` (как у двух других аккаунтов).
2. Засвеченные в переписке OAuth-коды одноразовые и, скорее всего, уже погашены,
   но аккуратнее их перевыпустить.

Для тестов достаточно фейковых токенов: панель принимает любую строку, бот просто
не подключится к Twitch — весь CRUD и настройки при этом проверяются полностью.

## 6. Как повторить прогон

```bash
# панель должна быть поднята на :8000
curl -s -X POST localhost:8000/api/accounts -H 'Content-Type: application/json' \
     -d '{"nickname":"modbot","token":"test_token_modbot"}'

# роль (внимание: поле называется role, а не bot_role)
curl -s -X PUT localhost:8000/api/accounts/1/role \
     -H 'Content-Type: application/json' -d '{"role":"moderator"}'

# обход всех превью-URL виджетов
.venv/bin/python scripts/qa_preview_sweep.py

# скриншоты виджетов в обход залипшей браузер-сессии (§4.1)
.venv/bin/python scripts/qa_shoot.py

# исполнение виджетов в реальном DOM (нужен jsdom)
npm install --no-save jsdom && node scripts/verify_widget_runtime.js

# markdown-ссылки не битые
.venv/bin/python scripts/check_md_links.py
```
