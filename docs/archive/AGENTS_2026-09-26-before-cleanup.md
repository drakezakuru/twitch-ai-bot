# AGENTS.md — правила работы в этом репозитории (ОБЯЗАТЕЛЬНО К ИСПОЛНЕНИЮ)

Этот файл читает любой агент, работающий в репозитории. Он про то, как безопасно менять код и не терять работу.

> **ОБЯЗАТЕЛЬНО К ПРОЧТЕНИЮ перед любой работой:**
> 1. **`docs/PRODUCT_RULES.md`** — жёсткие продуктовые и quality-инварианты.
> 2. **`PLAN_TODO.md`** — единственный активный план и все нерешённые вопросы.
> 3. **`docs/DECISIONS.md`** — принятые владельцем решения; не переоткрывать их молча.
> 4. **`docs/ARCHITECTURE.md`** — постоянные scope/storage/runtime контракты.
> 5. Для отдельной future-функции — только её файл из `docs/specs/`.

> Старые планы и audit-ledgers находятся в `docs/archive/` и не являются source of truth.
> `FILE_ZONES.md` — только компактная карта модулей.
>
> **Решение владельца 12.09.2026 (`DEC-OWNER-001`): параллельные агентские сессии отменены.**
> Работа всегда идёт в этой папке (`twitch-ai-bot/`) в текущей ветке. Новые git worktree и ветки
> `session/*` не создаются; оставшиеся папки `session-*/` вне проекта — исторические копии,
> их нельзя ни удалять, ни редактировать.

## 1. Ветка и коммиты

- Работай в текущей ветке задачи (её показывает окружение). Не создавай новых веток и не
  переключайся на чужие без явного запроса владельца.
- **Коммить после каждого завершённого шага**, когда профильные тесты зелёные (см. §3).
- Один пункт плана = один маленький коммит + затронутые тесты + grep остаточных ссылок.

### 1a. Отдельный контекст для Hoplite

- Если агент работает в среде Hoplite, ветку определяет окружение Hoplite; устаревшее имя ветки
  в плане не является командой переключиться на неё.
- После каждого завершённого пункта `PLAN_TODO.md`, когда focused tests и `git diff --check`
  зелёные, Hoplite обязан не только создать локальный коммит, но и опубликовать этот exact commit
  в текущую разрешённую GitHub-ветку через first-party source-control tools.
- Следующий пункт плана начинается только после подтверждённой публикации предыдущего коммита.
- Hoplite не публикует незавершённые шаги, красные тесты, production data, credentials или
  временные артефакты.

## 2. ЗАПРЕЩЕНО (без явного запроса владельца)

- ❌ `git stash` / `git stash pop/apply`, `git checkout -- <файл>`, `git restore`,
  `git reset`, `git checkout <branch>` — это уже приводило к потере ~8000 строк (28.08.2026).
- ❌ Переписывать целый файл своей устаревшей копией (read → полный overwrite). Сначала
  перечитай файл с диска, потом правь точечными Edit-ами.
- ❌ `git push`/`git commit` в чужие ветки.

## 3. Тесты — гонять ТОЛЬКО профильные, не весь suite

> Полный `pytest tests/` идёт ~20 минут: `openai-whisper`/`torch` тянут ~1.5 ГБ ML-зависимостей
> (nvidia/triton) и медленно импортируются. Полный прогон почти никогда не нужен.

- ✅ **По умолчанию** гоняй только тесты своей задачи:
  `pytest tests/test_<модуль>.py -q` (например `tests/test_bot_roles.py`).
- ✅ Быстрый sanity одной командой (без ML-тяжести) — только затронутые файлы через `-q`.
- ⏭ **Не запускай** без явной просьбы: полный `tests/`, а также ML-зависимые
  `test_diarization.py`, `test_stream_vision.py`, `test_stream_source_custom.py`,
  `test_s12_voice_clone_f5.py` (требуют whisper/torch/numpy/scipy).
- ✅ У каждого прогона своя `data/bot.db` (изоляция в `tests/conftest.py`), базы не конфликтуют.
- Полный suite и запуск панели/браузера — **только по явному «поехали» владельца.**

## 4. Правка общих файлов — точечно, не переписыванием

- `app/routes.py`, `static/app.js`, `templates/*` — только точечные вставки/Edit-ы,
  не полный overwrite. Новые HTTP-эндпоинты — в своём `app/<фича>_routes.py` +
  one-line `include_router` в `app/server.py`.
- В `static/app.js` — аппендить свою секцию в конец (`// ── <Фича> ──`) и точечные правки.
- `database.py` — новые таблицы своей фичи через `<фича>.ensure_schema()`, вызываемый
  из init_db одной строкой; existing-строки читать, схему не ломать.

## 4b. Файловые зоны (`FILE_ZONES.md`)

- Реестр зон — карта ответственности за модули. **Тестов на md-файлы в проекте нет**
  (`DEC-OWNER-012`, удалены 13.09.2026): карта поддерживается руками — при удалении или
  переносе файла правь строку зоны в том же коммите.
- Ссылки в активных документах проверяются вручную: `python3 scripts/check_md_links.py`
  (~0.1 c, не часть тестового прогона).

## 5. Корень проекта — держать чистым (решение владельца, 28.08.2026)

- **НЕ создавать в корне** новые CLI-скрипты, утилиты, разовые .py-файлы. Всё это — в `scripts/`
  (пример: `scripts/run_bot.py`). Временные файлы — в `/tmp/opencode`.
- В корне остаются: `run.py`, `start.sh/start.bat/start_bg.sh`, конфиги
  (`requirements*`, `pytest.ini`, `.env.example`, `Dockerfile`, `docker-compose*.yml`),
  ровно четыре рабочих `.md` (`README.md`, `AGENTS.md`, `PLAN_TODO.md`, `FILE_ZONES.md`),
  папки `app/static/templates/tests/widgets/scripts/data/logs`.
  Остальные планы и аудиты — история, они лежат в `docs/archive/` (перенос 04.09).
- Скриптам в `scripts/` — bootstrap в начале (sys.path на корень + chdir), см. `scripts/run_bot.py`.
- Владелец запускает ботов ТОЛЬКО через панель (`run.py`); standalone `scripts/run_bot.py`
  не используется — при сомнениях не трогать.
- Удаление/архивация устаревших docs выполняется только по `PLAN_TODO.md`, отдельным коммитом,
  после переноса незакрытых пунктов и проверки ссылок.

## 6. Если работа «пропала»

1. `git log --all --oneline` и `git reflog` — ищи ветки/коммиты.
2. `git stash list` — проверь стэш (НЕ pop). Единственный исторический стэш (28.08.2026,
   слепок эпохи v11) разобран 12.09: содержимое лежит текстом в
   `docs/archive/STASH_2026-08-28_widgets-v11.patch` (`DEC-OWNER-008`), сам стэш удалён.
3. Сообщи владельцу, НЕ откатывай файлы «назад» — так теряется работа.
