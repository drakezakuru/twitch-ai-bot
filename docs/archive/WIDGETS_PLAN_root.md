## 0. Аудит текущего состояния (что уже есть в коде)

Зафиксировано перед началом работ, чтобы не терять контекст между шагами реализации:

- `app/widgets.py` (5446 строк, ~112 роутов) — уже реализованы: goals, sub-goal,
  donation-top / top-donators, schedule, song-request (с очередью, priority, boost,

  mascot, anime-runner, lower-third, now-playing, recent-events, stream-session,
  donation-challenges, latest-event-card. Весь HTML/CSS/JS каждого виджета встроен как
  Python-строка внутри `app/widgets.py` — отдельной папки под виджеты не существует.
- **Два несвязанных TTS-оверлея** (важная находка, влияет на разделы 2 и 8):
  - `/obs/tts` (`app/routes.py:2251`) — **живой** роут. Подключается к `/ws`, слушает
    события чата (`type: chat`) и озвучивает их сам через **браузерный Web Speech API**.
    Игнорирует реальный TTS-движок (`app/tts_engine.py`) и его провайдеров
    (ElevenLabs/Piper/XTTS) — просто читает сырой текст чата. **Явно вырезает эмодзи**
    регуляркой перед озвучкой.
  - `templates/obs_tts_widget.html` — **мёртвый файл**, не подключён ни к одному роуту
    (ссылка на него осталась только в неиспользуемом `index_v10_backup.html`). Именно
    этот файл слушает событие `type: tts` с `audio_b64`/`provider`/`emotion` — то есть он
    и должен быть настоящим виджетом ответов TTS-движка бота, но сейчас никуда не смонтирован.
  - Итог: то, что сейчас реально стоит в OBS как `/obs/tts`, озвучивает **сырой чат**
    браузерным голосом, а не ответы TTS-бота через настроенного провайдера/голос.
    Требования владельца (золотой цвет, свой голос, эмодзи-брендирование, отдельный
    оверлей чата бота) относятся именно к «правильному» TTS-виджету бота, который
    нужно фактически создать/подключить.
- `app/tts_engine.py`: `TTSEngine.speak()` уже содержит **очередь с приоритетом**
  (`heapq`, `priority = 0` если `cfg["priority"] in ("streamer","high",1,True)`, иначе `10`).
  То есть инфраструктура очереди частично есть, но:
  - она только для TTS-сообщений одного бота, без слота под alert-звуки (донаты/сабы);
  - нет понятия «замолчать полностью» (mute/duck), только относительный приоритет очереди;
  - `broadcast_tts_event()` шлёт `type: tts` через общий `broadcast_log`, который слушает
    только несмонтированный `templates/obs_tts_widget.html`.
- `app/voice_clone.py` + `XTTSProvider`/`PiperProvider` (`tts_engine.py`) — уже поддерживают
  выбор отдельной голосовой модели `per account_id` (`tts_bot_config.voice`). Значит «свой
  голос для TTS-бота» технически не новая фича, а конфигурация — нужно только явно завести
  отдельный `account_id`/бот-профиль для TTS-бота и назначить ему клон/пресет голоса.
- `app/server.py:on_eventsub_event` — единая точка входа для `channel.subscribe`,
  `channel.cheer`, `channel.follow`, `channel.raid`; уже пишет в `recent_events` и
  инкрементит sub-goal. Это естественная точка для триггера «заглушить TTS».
  `app/widgets.py:on_donation_event()` — точка для донатов (может быть Twitch-донат через
  EventSub cheer, либо внешний webhook Streamlabs/DonationAlerts — сейчас в коде нет
  готового внешнего webhook-роута для донатов, только `on_donation_event()` как функция,
  вызываемая из `top_donators_add` вручную и предположительно из внешнего кода;
  **отдельный вопрос**, есть ли реальная интеграция с донат-сервисом — см. раздел 3).
- `app/chat_analyzer.py:_detect_chat_role()` (добавлено в §9c, PR #9) — уже умеет отличать
  `broadcaster`/`mod`/`vip`/`subscriber`/`viewer` по бейджам twitchio `Chatter`. Пригодится
  для виджета «модеры/VIP печатают» (раздел 6).
- Ни один существующий виджет не поддерживает произвольный «приоритет над остальным звуком»
  — все виджеты независимы друг от друга, нет общего аудио-диспетчера.

## 1. Общая архитектурная развязка — «Widget Audio Bus»

Прежде чем реализовывать разделы 3/4/7 (авто-молчание, пауза видео, общая очередь),
нужен один общий механизм координации звука/видео между виджетами, иначе каждая пара
"TTS ↔ алерт", "TTS ↔ song-request player" будет чинится отдельным хаком.

- [ ] Ввести на backend событие `widget_bus` в WebSocket-протоколе (`app/server.py`,
  через существующий `broadcast_log`), с типами:
  - `duck_start` / `duck_end` — «кто-то просит остальных стать тише/замолчать»
    (`{source: "donation"|"subscribe"|"raid"|"tts", reason, duration_ms?}`)
  - `pause_media` / `resume_media` — «кто-то просит поставить видео/медиа на паузу»
- [ ] Каждый OBS-виджет, который проигрывает звук/видео (TTS overlay, alert-виджет,
  song-request/now-playing плеер, если он видео), на клиенте подписывается на
  `widget_bus` и сам решает, как реагировать (замолчать, снизить громкость, поставить на паузу).
  Т.е. координация **декларативная** ("прошу тебя утихнуть"), а не «TTS напрямую дёргает DOM
  другого виджета» — виджеты физически в разных Browser Source в OBS и не имеют доступа
  друг к другу иначе как через WebSocket.
- [ ] `app/tts_engine.py:TTSEngine.speak()` перед синтезом проверяет флаг активного
  `duck_start` (in-memory, TTL по `duration_ms`) и либо откладывает сообщение в очередь,
  либо (если `hard_mute=True`) отменяет его совсем — конфигурируется per-событие
  (раздел 3).
- [ ] Тест: unit-тест на in-memory duck-state (start/end/TTL-истечение), интеграционный
  тест на то, что `on_eventsub_event("channel.subscribe", ...)` действительно взводит
  `duck_start` перед тем как что-либо озвучится.

**Открытое решение:** владелец не уточнил, должно ли TTS-сообщение при "молчании" —
(а) быть отложено и озвучено после отбоя тревоги, или (б) быть полностью пропущено.
Предлагаемая реализация по умолчанию: **отложить** (поставить в очередь, максимум на
X секунд, конфигурируемо), кроме случая переполнения очереди — тогда пропустить самое
старое сообщение. Это соответствует фразе «затыкался при донатах» (замолчать *на время*),
а не «игнорировать сообщения».

### 2.1 «Свой голос» — уточнение возможностей (доп. пожелание от 28.08.26, 14:33)

> Пожелание: «мб есть другие возможности голос дать боту не только через ттс, а что
> бы прям у него голос был» — то есть не просто выбор пресета в TTS, а более
> «настоящий»/узнаваемый голос конкретно для этого бота.

Технически в проекте уже есть 4 уровня «дать боту голос», от простого к сложному —
задача этого пункта не писать новый движок, а **явно разложить владельцу опции**
и довести выбор до понятного UI (раздел 2 выше это отчасти уже покрывает — здесь
уточнение объёма возможностей):

- [ ] **Уровень 1 — пресет провайдера** (уже есть, `tts_bot_config.provider` +
  `voice`): Web Speech (голоса браузера/ОС), Piper (локальные ONNX-модели голосов),
  ElevenLabs (облачные готовые голоса по `voice_id`). Никакого клонирования — просто
  выбор из готового списка, самый простой путь к «у бота свой голос» уже сегодня.
- [ ] **Уровень 2 — voice clone с нуля из аудио-образца** (`app/voice_clone.py`,
  `POST /api/voice-clone` в `routes.py:6540`): загрузить сэмпл голоса (свой, актёра,
  синтетический) → XTTS/Coqui (локально) или ElevenLabs Voice Clone API (облако,
  реальный клон голоса) → бот говорит именно этим голосом. Backend полностью готов
  (`provider IN ('elevenlabs','xtts','piper','playht','external')`), не хватает только
  явного UI-потока "создать голос для этого бота" на вкладке TTS (сейчас voice clones
  управляются отдельно от конкретного бота — нужно связать выбор в один клик).
- [ ] **Уровень 3 — внешний/сторонний voice-провайдер** (`provider = 'external'` /
  `'playht'` уже заведены в схеме БД как допустимые значения, но нет ни одного
  реального адаптера синтеза под них в `app/tts_engine.py` — только ElevenLabs/Piper/
  XTTS реализованы). Если владелец имеет в виду конкретный сервис (Play.HT, Fish
  Audio, любой другой voice-as-a-service) — нужно уточнить какой именно, и добавить
  адаптер по образцу `ElevenLabsProvider`/`XTTSProvider`.
- [ ] **Уровень 4 — real-time voice changer** (не то же самое, что TTS: голос
  оператора/стримера меняется живым голосом в реальном времени через VST/RVC-подобный
  voice-changer, а не через синтез текста). В текущем проекте этого нет вообще — это
  отдельная, значительно более сложная фича (аудио-пайплайн в реальном времени, а не
  разовая генерация по тексту). **Не начинаем без отдельного явного запроса** — здесь
  только фиксируем как теоретическую опцию 4-го уровня, на случай если именно это
  имел в виду владелец.

**Открытое решение:** предполагаем, что «голос боту не только через ттс» скорее всего
означает Уровень 2 (полноценный voice clone, а не просто пресет из списка) — это
самый разумный шаг вперёд без незнакомых новых интеграций. Уточнить у владельца перед
началом, какой уровень нужен (особенно важно для Уровня 3/4 — там нужны конкретные
названия сервисов/технологий, иначе делать нечего).

## 4. Координация с видео/медиа-виджетами — TTS может ставить видео на паузу

> Пожелание (c): «мог сам видео паузить например» — формулировка расплывчатая,
> ниже — предлагаемая интерпретация.

**Открытое решение (нужно потом подтвердить с владельцем):** в проекте нет "видео-виджета"
как такового (song-request/now-playing — это текстовый плеер, ссылка на трек, не видео
на OBS-сцене). Предполагаем, что речь про **любой** будущий или сторонний видео/медиа
Browser Source (например, source clip player, YouTube embed для донатов и т.п.), который
пользователь добавит сам — и TTS должен иметь возможность просигналить ему "пауза".

- [ ] Реализовать это через тот же `widget_bus` (раздел 1): при начале озвучки TTS
  (`TTSEngine.speak()` перед синтезом) отправлять `pause_media` в `broadcast_log`,
  а по завершении озвучки (или ошибке/фолбэку) — `resume_media`.
- [ ] Задокументировать в новой папке виджетов (раздел 5) простой JS-сниппет
  `widget-bus-client.js` для стороннего/самописного видео-виджета: подписаться на
  `pause_media`/`resume_media` через `/ws` и вызвать `video.pause()`/`video.play()`.
  Поскольку сторонние виджеты пользователя не находятся в этом репозитории, наша
  задача — обеспечить событие и дать готовый сниппет, а не переписывать чужой плеер.
- [ ] Если в будущем будет добавлен собственный видео-виджет в этом проекте (media-share/
  видео-оверлей) — подключить его к тем же событиям `pause_media`/`resume_media` "из коробки".
- [ ] Тест: unit-тест на то, что `speak()` шлёт `pause_media` перед синтезом и
  `resume_media` после (mock `broadcast_log`).

  открывается напрямую (`file://` или через любой статик-сервер) и настраивается через
  query-параметры и/или fetch к `/api/widgets/public/*` (публичный API уже CORS-открыт

  и вместо этого отдают файл из `widgets/<name>/index.html` (`FileResponse` или
  `Jinja2Templates(directory="widgets")` для тех виджетов, где нужна подстановка
  `__THEME__`/`__TITLE__` — оставить существующий `.replace()`-паттерн, просто источник
  шаблона теперь файл, а не Python-строка).

  их query-параметры продолжают работать как раньше, тесты не должны увидеть разницы.
- [ ] `app/server.py`: примонтировать `widgets/` как статику НЕ обязательно (роуты и так
  отдают файлы через FastAPI), но при желании владельца использовать виджеты вручную —
  задокументировать, что папку `widgets/` можно скопировать целиком и открывать файлы
  прямо в OBS без панели (для тех виджетов, что не зависят от `/api/widgets/public/*`
  бэкенда — то есть де-факто не все, а только «декоративные»; честно отметить в README
  какие виджеты требуют работающий backend, а какие полностью автономны).
- [ ] Обновить `templates/partials/widgets.html` (текущие карточки со ссылками) — без
  функциональных изменений, только подтверждение, что пути `/widget/*` не поменялись.
- [ ] Тесты: перегнать существующие widget-роут-тесты (если есть) и убедиться, что HTML
  ответ идентичен до/после переноса в файлы (byte-diff или хотя бы наличие ключевых

**Риск, требующий аккуратности:** это самый рискованный технический пункт всего плана —
рефакторинг затрагивает ~112 роутов в `app/widgets.py`. Делать **по одному виджету за раз**,
коммит на каждый, чтобы легко откатить конкретный виджет при регрессии, а не одним
огромным патчем.

## 6. Виджет озвучки чата и/или «модеры/VIP печатают»

> Пожелание (e): «нужен отдельный виджет для озвучивание сообщений из чата ИЛИ оверлей
> типо модеры пишут или виперы, и команду типо какую-то ИЛИ без нее — сразу два давац»
> («оба варианта пожалуйста»).

Это **два разных виджета** — оба нужны:

### 6.1 Chat Reader — озвучка сообщений чата вслух

- [ ] Отдельный виджет `widgets/chat-reader/` (публичный роут `/widget/chat-reader`),
  который в отличие от текущего `/obs/tts` (раздел 2) — специально предназначен читать
  **обычные сообщения чата** (не ответы бота), с фильтрами: канал, минимальная роль
  (уже есть паттерн `min_role`/`ROLE_RANK` в `/obs/tts` — переиспользовать), и **явным
  режимом команды**:
  - Режим "без команды" (`trigger_mode=all`) — читает все сообщения подряд (как сейчас
    `/obs/tts`, но с настоящим TTS-провайдером бота вместо Web Speech).
  - Режим "по команде" (`trigger_mode=command`, дефолтный триггер `!read` или
    настраиваемый) — читает только сообщение, начинающееся с команды, аналогично
    существующему паттерну `!sr <название>` в `chat_analyzer.py:1296-1302`
    (`add_song_request`). Новая функция `read_chat_message()` в `app/widgets.py` по
    тому же образцу, вызывается из `chat_analyzer.on_message()`.
- [ ] Настройка обоих режимов **одновременно доступна** через админ-форму (чекбокс
  "читать все" + отдельное поле "команда для чтения по запросу") — то есть не выбор
  "или/или", а оба канала включаются/выключаются независимо, как и просил владелец.
- [ ] Использует общую TTS-очередь (раздел 7), не выбивается вперёд TTS-бота без причины.

### 6.2 Typing Indicator — «модеры печатают» / «VIP печатает»

- [ ] Новый публичный роут `/widget/typing-indicator` + WebSocket-событие `typing_start`/
  `typing_stop`, посылаемое из `chat_analyzer.on_message()` **до** обработки сообщения
  бота (используя уже существующий `_detect_chat_role()` из §9c) — событие шлётся при
  получении сообщения от роли `mod`/`vip`/`broadcaster` (обычный `viewer` не показывается,
  иначе виджет будет мигать на каждое сообщение чата).
  Технический нюанс: у Twitch IRC/EventSub нет реального "человек печатает" события
  (в отличие от Discord) — единственный доступный сигнал — "только что отправил
  сообщение". Виджет показывает роль отправителя **на короткое время после отправки**
  сообщения (например 3 сек), а не "печатает прямо сейчас". Это единственная технически
  честная реализация без доступа к клавиатурным событиям пользователя в браузере Twitch.
  **Явно документируем это ограничение владельцу**, чтобы не создавать ложных ожиданий.
- [ ] Настройка: какие роли показывать (mod/vip/broadcaster — чекбоксы), длительность
  показа, текстовые шаблоны ("Модератор {user} в чате", "VIP {user} в чате").

## 8. Эмодзи-брендирование TTS-сообщений + отдельный чат-оверлей TTS-бота

> Пожелание (g): эмодзи в начале И в конце сообщения TTS-бота, плюс отдельный
> оверлей-виджет чата именно для TTS-бота.

- [ ] `tts_bot_config`: новые колонки `emoji_prefix TEXT DEFAULT ''`,
  `emoji_suffix TEXT DEFAULT ''` (миграция через `_add_column_if_missing`, паттерн
  как в §9c/`speed`).
- [ ] `TTSEngine.speak()` — перед отправкой в `broadcast_tts_event()` и (если владелец
  хочет также вставлять эмодзи в сам произносимый текст, не только в визуальный оверлей)
  перед синтезом, оборачивать `text` в `f"{emoji_prefix} {text} {emoji_suffix}"`.
  **Открытое решение:** эмодзи скорее всего нужны только в **визуальном** отображении
  (в тексте на оверлее), а не в самой озвучке голосом (эмодзи не читаются TTS-провайдерами
  осмысленно). Предлагаемая реализация по умолчанию: эмодзи добавляются в `text`, который
  идёт и в оверлей, и в синтез — большинство TTS-движков (Web Speech, ElevenLabs, Piper)
  просто пропускают несловесные символы при синтезе, так что риска "бот озвучит эмодзи
  словами" нет на практике, но если тестирование покажет иначе — сделать `visual_text`
  отдельным от `speech_text` полем в событии `broadcast_tts_event`.
- [ ] Важно: убрать/пересмотреть текущее вырезание эмодзи в `/obs/tts`
  (`app/routes.py:2251`, регэксп `[\u{1F300}-\u{1FAFF}]`) — эта логика относится к
  "сырому" виджету чата (раздел 2, открытое решение), не трогаем её для `chat-reader`,
  но для нового `tts-bot`-виджета (раздел 2) эмодзи-брендирование не должно попадать под
  этот фильтр — они разные виджеты с разным кодом, конфликта не будет само по себе, но
  явно отметить в комментариях, чтобы не скопировать фильтр по ошибке при рефакторинге раздела 5.
- [ ] Новый публичный виджет `widgets/tts-chat-overlay/` (роут `/widget/tts-chat-overlay`)
  — отдельный от общего `chat-highlight`/`obs-widget` оверлей чата, который показывает
  **только** реплики TTS-бота (текст + эмодзи-обёртка + золотой акцент из раздела 2),
  подписываясь на тот же `type: tts` WS-эвент, что и голосовой оверлей — то есть у
  TTS-бота получается **два** синхронных виджета (голос+текст-пузырь как в разделе 2, и
  отдельная лента истории реплик как в этом пункте), что соответствует фразе владельца
  "у этого бота был отдельный оверлей виджет чата" отдельно от голосового оверлея.
- [ ] Админ-форма на вкладке TTS: поля "Эмодзи в начале" / "Эмодзи в конце" (текстовый
  инпут, поддержка emoji picker если легко подключить существующий UI-компонент,
  иначе обычный `<input type=text>` с плейсхолдером-подсказкой).
