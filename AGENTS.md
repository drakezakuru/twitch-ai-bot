# AGENTS.md — как работать в этом репозитории

Правила для любого агента, который берётся за эту задачу. Цель — не потерять работу и не
сломать то, что уже сделано. Переписано 27.09.2026 для ясности; смысл правил не изменился.

## Что прочитать перед началом

1. [`docs/PRODUCT_RULES.md`](docs/PRODUCT_RULES.md) — что это за проект и какие правила
   качества нельзя нарушать.
2. [`PLAN_TODO.md`](PLAN_TODO.md) — единственный активный план: что уже сделано, что ждёт
   владельца, что в очереди.
3. [`docs/DECISIONS.md`](docs/DECISIONS.md) — решения владельца. Их нельзя тихо пересматривать.
4. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — постоянные технические контракты.
5. Если работаешь над одной конкретной функцией — прочитай её файл в `docs/specs/`.

`docs/archive/` — это история, а не текущая правда: не опираться на неё при принятии решений.
`FILE_ZONES.md` — короткая карта «какой файл за что отвечает».

## Правило 1 — одна ветка, один шаг, один коммит

- Работаем в той ветке, которую задала задача. Новые ветки и git-worktree не создаём, на чужие
  ветки не переключаемся. Папки `session-*/` вне проекта — это старая историческая копия;
  их не трогать (решение `DEC-OWNER-001`).
- Один законченный пункт плана = один небольшой коммит. Перед коммитом: профильные тесты
  зелёные, `git diff --check` чистый, нет забытых ссылок на переименованное/удалённое.
- Публикуем (коммитим и пушим) сразу после каждого готового шага, потом берём следующий.
  Не публикуем: недоделанные шаги, красные тесты, боевые данные, ключи/токены, временные файлы.

## Правило 2 — без явного разрешения владельца нельзя

- ❌ `git stash`/`pop`/`apply`, `git checkout -- <файл>`, `git restore`, `git reset`,
  `git checkout <ветка>`. Один раз это уже стоило ~8000 строк потерянной работы (28.08.2026) —
  правило появилось из-за этого.
- ❌ Переписать файл целиком своей устаревшей версией. Сначала перечитать с диска, потом
  вносить точечные правки.
- ❌ Коммитить и пушить в чужие ветки.

## Правило 3 — тесты запускаем прицельно, не всё подряд

- По умолчанию гоняем только то, что относится к правке: `unset PYTHONPATH && python3 -m pytest tests/test_<модуль>.py -q`
  и `node --test tests/<имя>.test.js`.
- Полный прогон `tests/` (~20 минут, тянет тяжёлые ML-зависимости) и отдельные ML-тесты
  (`test_diarization.py`, `test_stream_vision.py`, `test_stream_source_custom.py`,
  `test_s12_voice_clone_f5.py`) — только если владелец явно попросил.
- У каждого запуска тестов своя чистая база (`tests/conftest.py` создаёт её сам).
- Скриншоты панели на тестовых данных — можно без спроса. Реальный Twitch, реальный OBS,
  боевая база и настоящие внешние провайдеры — только после явного «поехали» от владельца.

## Правило 4 — общие файлы правим точечно, не переписываем целиком

- `app/routes.py`, `static/app.js`, `templates/*` — только маленькие точечные вставки.
  Новый эндпоинт — в своём файле `app/<фича>_routes.py`, подключается одной строкой
  `include_router` в `app/server.py`.
- `static/app/*.js` — новый код своей фичи оформляем отдельной секцией в конце файла
  (`// ── <Фича> ──`), остальное не трогаем.
- Новая таблица в базе — через `ensure_schema()` своего модуля, подключается одной строкой
  из `init_db`. Существующую схему не ломаем; старые записи помечаем как устаревшие, а не
  удаляем молча.
- Если файл переименован или удалён — в том же коммите поправить его строку в `FILE_ZONES.md`
  и проверить ссылки: `python3 scripts/check_md_links.py`.

## Правило 5 — корень проекта держим чистым

- Новые разовые скрипты и `.py`-файлы — не в корень, а в `scripts/`. Временные файлы — в
  `/tmp/opencode`.
- В корне остаются только: `run.py`, `start*.sh/.bat`, конфиги (`requirements*`, `pytest.ini`,
  `.env.example`, `Dockerfile`, `docker-compose*.yml`) и четыре документа: `README`, `AGENTS`,
  `PLAN_TODO`, `FILE_ZONES`.
- Ботов владелец запускает только через панель (`run.py`); `scripts/run_bot.py` не трогать.
- Удалять или архивировать старые доки — только по плану, отдельным коммитом, с проверкой ссылок.

## Если показалось, что работа пропала

1. Сначала посмотреть: `git log --all --oneline` и `git reflog` — коммиты почти всегда на
   месте, просто не в той ветке, которую видно по умолчанию.
2. `git stash list` — можно посмотреть список, но не трогать (`pop`/`apply` — под запретом).
3. Сообщить владельцу и ждать его решения. Никогда не пытаться «откатить как было» самому.
